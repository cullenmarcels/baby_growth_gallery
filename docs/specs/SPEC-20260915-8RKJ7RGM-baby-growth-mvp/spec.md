# 首个宝宝成长记录业务里程碑规格

## 目标与交付链

在已归档的账号会话与家庭身份基础上，按 Plan C–H 顺序交付“宝宝档案 → 照片上传 → 图集/时间轴/详情 → 里程碑 → 成长数据 → 首页聚合”的真实业务闭环。每个阶段独立从最新 `origin/develop` 建立 feature 分支、验收、集成和归档，后续阶段不提前占用旧基线。

本里程碑是可验收的封闭测试版，不是公开生产版本。真实短信、正式法律文本、公开运营、发布晋升与 Tag 均由后续独立工作处理。

## 跨阶段身份与权限

- 一个家庭支持多个宝宝；宝宝只能属于一个家庭。Session 保存 `activeBabyId`，仅在当前 Session 内记忆，切换家庭或宝宝失效时由服务端重新校验并确定性回退。
- OWNER/ADMIN 创建、编辑、归档和恢复宝宝档案，并可管理家庭全部已发布内容；所有 ACTIVE 成员可上传照片、记录里程碑和成长数据。
- 内容作者管理自己的照片、里程碑和成长记录；非作者 MEMBER 只能查看。所有服务端资源请求重新查询 ACTIVE Membership，不信任前端角色、familyId 或 babyId。
- 页面错误、确认和失败状态全部使用中文；前端根据稳定机器错误码映射文案，不直接渲染底层异常或英文详情。

## Plan C：宝宝档案基础

- `BabyProfile` 保存 familyId、创建者 Membership、1–30 字符昵称、必填出生日期、可空 MALE/FEMALE、ACTIVE/ARCHIVED/PURGING 状态、归档/清理时间及审计时间。
- `AccountSummary` 增加 `activeBabyId:string|null`。当前宝宝有效则保留；否则在当前家庭按 `(createdAt DESC,id DESC)` 选择最近 ACTIVE 宝宝；没有则为 null。
- OWNER/ADMIN 可以创建、编辑、归档和恢复；MEMBER 可以查看和切换。归档后从普通页面隐藏，30 天内可恢复，之后不可逆清理。
- 清理由 PostgreSQL 驱动的幂等维护任务执行，使用 advisory lock、批量扫描和可重试状态；Plan C 清理宝宝档案，后续 Plan 逐步扩展到照片对象、里程碑、成长记录和 Activity 墓碑。

## 后续固定边界

- Plan D：JPG/PNG/WebP，单张 20 MiB、单批 20 张；S3 隔离上传、内容验证、去 EXIF/GPS、三种安全变体、创建者私有草稿 30 天、已发布照片回收站 30 天；照片全家庭可见。
- Plan E：真实图集、照片/里程碑时间轴、照片详情、上一张/下一张和从已发布照片选择宝宝头像；评论、反应和视频不实现。
- Plan F：12 项无医学期限的中性模板与自定义里程碑；用户加入清单后才计入进度；仅应用内日期提醒；允许关联最多 10 张已发布照片。
- Plan G：任意年龄记录身高/身长、体重和头围；性别存在时按 WHO 官方口径计算 z-score/百分位，0–60 月使用 2006 标准，61–203 月按 2007 可用指标分段；不输出诊断结论。
- Plan H：首页聚合真实照片、清单进度、应用内提醒和最新成长数据；移动底部保留时间轴、图集、里程碑、数据、家庭，顶部宝宝区进入首页。

## 数据生命周期与隐私

- 宝宝归档、照片回收站和草稿有效期均为 30 天。清理顺序必须保证对象存储文件最终删除，并把关联家庭动态最小化为通用墓碑。
- 照片位置仅为用户填写的地点文本，不保存经纬度；对象 Key、日志、测试和证据不得包含真实儿童或家庭识别信息。
- Redis 只保存 Session、限流和临时状态，不作为宝宝、照片、里程碑或成长数据的持久事实源。

## 验收原则

- 每阶段同步实现 375、834、1440 三视口以及正常、空、加载、错误、权限、冲突和必要过期状态。
- OpenAPI 是客户端唯一生成来源；Prisma migration 只前向增加，不重写既有共享 migration。
- 完成 Plan H 后必须以两个合成家庭成员跑通完整业务故事，且跨家庭、跨宝宝、草稿和归档数据均无泄漏，才能称为首个业务里程碑候选。
